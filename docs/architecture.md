# Implementation architecture

Status: agent-selected design under the user's delegation of routine behavior/storage decisions. The [spec](spec.md) is authoritative; [ADR 0001](adr/0001-desktop-stack.md) records the stack. These are contracts for future code, not claims of completed implementation.

## Responsibilities

One Electron application service coordinates writes. React views request operations and display results; they must not manage raw filesystem/SQLite operations.

| Module | Public contract | Complexity owned inside |
| --- | --- | --- |
| Library service | Query; edit metadata/sections; change status/archive | Identity, validation, view/search rules, metadata precedence |
| Import/recovery service | Plan import; resolve duplicates; replace; trash/restore/purge | Staged bytes, file validation, revision changes, crash reconciliation |
| Window/session coordinator | Open/focus book; open library; quit | One window per book, lifecycle, progress flushing, session ownership |
| Reader session | Open; navigate; search/cancel; size; capture/restore location; dispose | Format-specific rendering, stable locations, isolation, resource cleanup |
| Catalog/storage internals | Private to services | Transactions/migrations, relative paths, immutable file publication, recovery records |

PDF and EPUB are actual variants, so use format adapters behind a common session contract. Locations remain a discriminated union, not one generic page integer. Expose real capability differences: font resizing versus page zoom, missing outline, unavailable text. Engine objects stay inside adapters. No plugin framework or hypothetical database abstraction is needed.

Code organization (as implemented):

```text
src/main/       lifecycle, window coordinator, validated messaging
src/library/    catalog rules, metadata/sections/status, import/recovery
src/storage/    schema/migrations and managed-file internals
src/preload/    narrow typed application bridge
src/shared/     types shared by main, preload and renderer (IPC contracts)
src/renderer/   library window (src/library/) and reader shell/engine UI
src/readers/    session contract, PDF.js and foliate-js adapters
tests/          behavior/storage/Electron checks and tiny licensed fixtures
```

These are organizational defaults, not one class/file per responsibility.

## Process and content boundaries

- Main application services own catalog writes and validate commands. Expensive copying/hashing/extraction/search must not block the interactive main event loop. Use bounded jobs/workers where needed rather than a process per trivial operation.
- UI receives IDs, approved revision tokens, and structured data, not an arbitrary filesystem/SQL/Electron bridge. Validate the sender and window assignment for every privileged message.
- Progress includes book ID, revision ID, session generation, and monotonic sequence. Reject late/reordered writes and messages from a window not assigned to that book. Session generation changes on replacement/reread/disposal.
- Implemented progress contract (M2-02, `src/library/progress.ts`): the generation is durable. `beginReaderSession` advances `books.session_generation` and returns the current revision's last committed position/sizing, so opening or reloading a reader retires any earlier session. `saveProgress` parses the untrusted message and then, in one `BEGIN IMMEDIATE` transaction, requires a live book, the current revision, the live generation, a matching format and a sequence above the stored one for that generation. It writes the position and per-book sizing together and acknowledges only after commit. `endReaderSession` retires a generation after its final flush. Replacement, deletion and reread must switch state and advance the generation in the same commit. Failures are typed (`invalid`, `unknown-book`, `stale-revision`, `stale-session`, `out-of-order`, `storage-failed`) and leave the last committed state unchanged. A committed save takes about 42 ms on the home HDD and runs synchronously on the main thread.
- Implemented reader IPC (M2-05, `src/main/sessions.ts`): `ReaderSessions` keys each session by the reader window's webContents ID. A catalog reader window calls `reader:open-book` with no arguments; main uses the book assigned to that window, starts a session (any earlier session of the window, such as before a reload, is flushed and retired first) and returns the grant with the current revision's bytes. The shell keeps the grant. It passes only the bytes and the saved position/sizing to its engine frame (`content.html?catalog`, per-book origin `borges://reader-catalog-<book-id>.reader`) and accepts messages only from that frame's window at that origin, never from chapter frames. It numbers the engine's positions and sends them over `reader:progress`. Main drops messages from unregistered or non-main frames, then rejects with `not-assigned` any write naming a book other than the window's, `stale-session` any other generation, and `out-of-order` any sequence at or below the last accepted one, before storage applies its own checks. Accepted positions are coalesced: the latest is committed 250 ms after the first pending one, and the result (`reader:progress-result`) is shown in the shell. A storage failure keeps the write pending for retry; other rejections do not raise the sequence floor. Reader regrant/reload strictly flushes and retires the earlier session; a failed flush retains the pending write and ownership. Forced destruction uses a best-effort final flush. Ordinary close/Quit and the other retirement paths first capture in-flight engine commands, as described below. `reader:opened` records a successful open (status rules in the library service) only for the window's current generation. The engine never receives the generation; a compromised engine could at most move its own book's position.
- Disable renderer Node integration; enable context isolation and sandboxing. Give only trusted application UI a narrow preload bridge. Isolate book content from that bridge and the application origin's privileges.
- External references (M5-02): adapters propose a plain address through the assigned engine document. The trusted shell checks both the source window and its assigned engine's per-book origin before showing a modal address/Copy Link dialog. It never opens a browser. Only an explicit dialog button calls `reader:copy-link`; main requires a registered reader's main frame and revalidates a bounded ordinary external URL before writing clipboard text. There is no clipboard-read endpoint or book-frame clipboard permission. The shared URL policy excludes local, app, script and data schemes. Internal links request navigation through the engine's command queue; navigation waits for foliate's queued source-link focus scrolling, then restores the destination anchor so later resize/font changes keep the new passage.
- Block book scripts, remote requests, top-level navigation, unsolicited windows, and arbitrary filesystem access. Resource serving permits approved revision/cover assets only, validates canonical paths, and rejects traversal/symlink escapes. Verify the design against foliate-js's CSP requirements during the spike; do not enable unsafe flags to render a sample.
- Bundle required PDF workers/fonts/CMaps and EPUB assets for offline use. Support permitted local images/fonts while blocking scripted/remote content.
- **Reader recovery (M5-03):** `src/main/reader-drain.ts` sends a fresh request token to the assigned shell. That shell relays it only to its engine; the engine pauses input and queues a final capture after earlier commands (including delayed pan). It sends position before completion; the shell relays both in order. Main accepts completion only from the registered main frame, matching owner and token; it then strictly commits the captured position. Requests coalesce, time out after five seconds, and clean up on renderer destruction. Close/Quit failures default to keeping the reader open; the user may explicitly discard unsaved changes. Quit keeps captured readers paused until all have answered, rejects new window opens during preparation, and resumes them if cancelled. Retry saving uses the same barrier. Replacement, revision restoration, duplicate-import replacement, deletion and reread await capture before synchronous save/retirement; replacement transactions still recheck the target and cancellation. Failed capture/commit leaves the reader usable; existing reload/recovery paths release a successfully retired reader. No new storage schema or book-frame bridge is introduced.
- **Reader failure UI (M5-03):** the trusted shell tracks reported versus committed sequence numbers and distinguishes pending, acknowledged and failed saves. Save failures retain Retry saving plus a precise storage reason; load/engine failures independently retain Retry reader, confirmed Replace file (bound to the sender's assigned book) and Open library. Successful saves cannot clear a load failure. Engines retain the last working report across a failed command so a partial internal move cannot become an acknowledged position. Invalid jump/size values use `ReaderInputError` and stay beside the controls. Exact restoration stays quiet; approximate/chapter and beginning fallbacks remain visible notices. Unexpected termination resumes the committed SQLite position/settings.
- **Content crash containment (M5-04):** concurrent books use distinct sites (`borges://reader-<source>-<book-id>.reader`) rather than the earlier shared `borges://reader` site. The shell CSP permits only `borges://*.reader` frames; main still permits only the exact assigned engine URL and that engine's own chapter blob origin. Resource serving recognizes bounded reader host names and retains its entry/assets-only, canonical-path and symlink checks. Book bytes/session grants are not served at those URLs. The shell's progress/link/drain messaging checks its assigned engine window and exact origin.
- A native SIGKILL leaves a disposed direct `WebFrameMain` without a shell `render-process-gone` event in this Electron version. Main checks direct engine-frame disposal every 500 ms while each reader window exists, reports each disposed frame once and removes the monitor on closure. It skips crashed shells. The surviving catalog shell rejects further engine messages, removes the dead frame and shows the existing retry/replace/library actions with an in-flight-loss explanation. There is no automatic restart loop. Retry uses normal strict flush/regrant and a fresh frame; positions already received by main can still be committed, and old-generation writes are rejected after regrant. Close/Quit can settle the received position without waiting on a dead engine. This is content-process recovery; it does not restart a crashed main process or recover unreported commands. See [native evidence](development.md#reader-crash-containment-m5-04) and Electron's [frame lifecycle API](https://www.electronjs.org/docs/latest/api/web-frame-main).
- Use a single-instance coordinator and an exclusive configured-library lock before writing. A second ordinary launch routes to the first, which reopens or reuses its library window and requests activation. Another build/process holding a root lock must yield an explanation, not competing writers. Verify lock ownership before stale-lock recovery.
- Startup refusals use `src/main/startup.ts`: an independent static window with escaped diagnostic text, JavaScript disabled, no preload and no external resources or navigation. It requires neither a working catalog nor normal renderer/IPC startup. Closing it exits 1; second launches request activation of that window. After successful catalog opening, reconciliation runs behind the existing offline boundary before any library work. Main retains unresolved messages for the library-only `library:startup-problems` endpoint; the library renders them as text across reloads and view changes. A failed reconciliation is reported while browsing remains available; the next process start retries it.
- Implemented root lock (M2-01): one SQLite connection holds an `EXCLUSIVE` lock (`locking_mode = EXCLUSIVE`, a POSIX advisory lock) on `library.lock` for the process lifetime. The kernel releases it when the holder exits or is killed, so successfully acquiring it is the ownership check; no PID heuristics or lock-file deletion are involved. `library.lock-owner.json` only names the holder in conflict explanations and is replaced after acquisition, which is reported as stale-lock recovery. The holding process must never open/close `library.lock` through `node:fs`, because closing any descriptor drops that process's POSIX locks. The root must be on a local filesystem with working POSIX locks.

Primary references: [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [security](https://www.electronjs.org/docs/latest/tutorial/security), [lifecycle/single-instance APIs](https://www.electronjs.org/docs/latest/api/app), [foliate-js](https://github.com/johnfactotum/foliate-js).

Diagnostic fixture readers still use bundled allowlisted fixtures and hold no progress session; catalog readers receive their bytes over IPC as described above. Canonical bundle paths, assigned frame navigation and malicious-content checks are verified in [M1-05 evidence](development.md#adversarial-readerresource-isolation-m1-05). Sender/revision/generation/sequence validation for catalog readers is verified natively by M2-05; cover grants remain for the library UI.

Personal delivery (`mise run package`) uses the same built main/preload/readers as the diagnostic artifact. Its trusted package manifest is named `borges`; the diagnostic manifest remains `borges-runtime-check`. Main selects the diagnostic controls/fixture endpoint only for unpackaged or diagnostic builds. Personal builds omit fixture bytes, use the `borges` runtime profile under Electron's app-data/config directory, and keep durable data in the separately configured library root. The launch script clears development/Node overrides and can select an absolute library root; the desktop installer uses bundled Node and writes a per-user launcher, without a runtime server or new application bridge. See the [user guide](user-guide.md) and [delivery evidence](development.md#personal-arch-delivery-m6).

## Library service (M2-04)

`src/library/query.ts`, `sections.ts` and `books.ts` implement the library service against the catalog; inputs are validated as untrusted and failures are typed `LibraryError`s (`invalid`, `unknown-book`, `unknown-section`, `name-conflict`, `section-cycle`, `storage-failed`). Writes run in one `BEGIN IMMEDIATE` transaction.

- **Scope in one place:** `scopedBooks` applies deleted (never shown), archived (hidden unless `includeArchived`; Archive shows only archived) and view (All Books, Unfiled, section branch, Currently Reading, Finished, Archive) scope in one SQL query. Search terms, author/subject filters and sorting run in JavaScript over that result, with `Intl.Collator` ordering (base sensitivity, numeric).
- **Normalization:** `foldKey` (NFKC, case folding via upper-then-lower, trimmed, repeated whitespace collapsed) is the single comparison key. Stored `sections.name_key` and `book_subjects.label_key` hold it, so changing it requires a migration that rewrites them. Search terms are substrings of folded fields, so SQL wildcards are literal.
- **Sections:** sibling names are unique by key (root siblings included); moves into the branch itself are rejected before the schema trigger. Deletion reports the branch's section, affected-book and newly unfiled counts for confirmation and relies on the schema's cascade.
- **Status:** `recordSuccessfulOpen` is called only after a reader rendered the book. `startRereading` sets Currently Reading, clears Archive, deletes the current revision's position and advances the session generation in one commit; the coordinator must flush and stop the open session first and restart it with a new grant.
- **Metadata:** `editMetadata` replaces title, ordered authors or the subject set and marks only the edited fields manual. Replacement refreshes available nonmanual fields and preserves useful old values when extraction supplies none, including intentional manual clears.
- **IPC (M3-01, `src/main/library-ipc.ts`):** every service operation has a `library:*` channel that only the library window may call; any other sender gets a thrown refusal. Arguments go to the service unchanged, so its validation is the boundary. Results are `{ok: true, value}` or `{ok: false, code, message}` with the `LibraryError` code (`failed` for anything else), because Electron's invoke would reduce a thrown error to text. After each successful change, and after a reader's successful open, main sends `library:changed` to the library window, which re-queries. `library:start-rereading` flushes and retires an open reader's session, resets the book, then reloads that reader, which starts a new session at the beginning; the old page's generation is stale. Archive, Unarchive and Finish leave readers open.

## Data model

Use foreign keys and versioned migrations. Exact SQL/indexes are implementation details; preserve these meanings. Schema 1 implements them in `src/storage/schema.ts`; later changes append forward-only migrations:

| Record | Meaning |
| --- | --- |
| Book | Stable ID, current revision, reading status, archive/delete timestamps, created/updated/last-opened times |
| Revision | ID/owning book, format, relative path, hash/size, original display filename, created/retired times, extracted metadata |
| Metadata | Effective title, ordered authors, flat subjects, cover, field-level manual-override provenance |
| Section/membership | Parent/name and many-to-many book membership; no cycles or duplicate memberships |
| Position | Revision-specific PDF page/normalized pan or EPUB locator/chapter/fraction, sequence/update time |
| Reader settings | Book and format-compatible font/fit/zoom settings |
| Recovery operation | ID/type/state, involved IDs, staged/published paths, enough outcome data for reconciliation |
| Trash state | Deleted book or retired revision with enough file/location/catalog context to restore |
| Library metadata | Library identity/schema version, independent of absolute root path |

Invariants:

1. A live book has one current revision, referencing published bytes rather than a partial staged file.
2. Revisions are immutable. Membership never copies/moves bytes. Source paths are provenance, not mutation targets.
3. Position belongs to a revision. A retired session cannot overwrite replacement progress. Status/archive/manual metadata belong to the book.
4. Trash/recovery records retain their bytes until explicit purge. Purge must not delete a live revision or still-referenced cover/resource.
5. Durable paths are relative. Titles/filenames are display metadata, not identity.
6. Manual override provenance includes explicit empty optional values, so extraction cannot resurrect cleared metadata.

Normal queries restrict deletion/archive/view scope in one place. Duplicate candidates use current live revisions, including archived entries; Trash-only matches use restore handling. Hashes identify equality candidates; metadata only suggests identity. UI and SQL validation must agree on normalization/uniqueness.

## Filesystem/database consistency

SQLite transactions do not include filesystem changes. Implement immutable publication plus a recoverable operation protocol:

1. Allocate operation/revision IDs and record pending work. Stream into private staging on the library filesystem while hashing; validate candidate content with bounded resources. Failure/cancellation leaves the old book unchanged.
2. Resolve duplicate choices against current catalog state. Recheck the target before commit; an old preview is not permission to overwrite a changed entry.
3. Before replacement/deletion/reread of an open book, save its old position, stop the old session, and advance session generation.
4. Publish complete bytes to an immutable final path using same-filesystem rename and appropriate durability handling. Retain enough operation state to reconcile a crash around publication.
5. Commit new-book/current-revision/metadata changes and old-revision retirement together in SQLite. Mark the operation complete only after catalog references point to published bytes. Retain old file/location in Trash.
6. Refresh views/reload the reader after commit. Precommit failure retains/reopens the old revision. A notification/reader failure after commit does not undo or misreport the committed catalog change; report it as a reader error and preserve the previous revision in Trash. Clean up only artifacts whose status/references are known.

Implemented for import (M2-03, `src/library/import.ts` and `recovery.ts`): states `pending` (partial copy may exist at `staged_path`), `staged` (digest recorded; bytes at `staged_path`, or at `published_path` after an interrupted rename), `published`, then `committed` in the same transaction as the book/revision rows. Each state is committed only after the step it records is durable (file fsync; directory fsync after rename/unlink). An import that did not commit is rolled back, both after an in-process failure and at startup: only record-named regular files are removed, and a complete copy only when it matches the recorded digest, then the operation is `abandoned`. The untouched source can be imported again. Uncertain leftovers are retained and the operation is marked `failed`, which startup reports each time and never touches. A removal that fails leaves the state unchanged so the next start retries. Unrecognized `staging/` and `files/` entries are reported and kept. Cover publication (M3-05, `src/library/covers.ts`) uses the same states with kind `cover`: copy a bounded PNG/JPEG to staging, decode and normalize it into a PNG thumbnail there, record its digest, publish to `covers/<operation-id>.png`, and atomically update the book’s manual cover and operation state. Rollback verifies operation-owned paths and cover references (effective book covers and extracted revision covers); it preserves uncertain or referenced bytes. Committed cover operations account for superseded cover bytes, which remain until explicit cleanup. Unrecognized `covers/` entries are also reported and retained. Replacement (M4-03) uses kind `replace` in the same publication protocol: before the catalog commit its new copy rolls back; committed replacement and old Trash revisions remain untouched. Its rollback checks operation-owned paths and any revision referencing the candidate ID/path, rather than treating the existing target book as a reference to the new copy. Delete and deleted-book restore are catalog-only atomic transitions (M4-05, below); revision restore is described under M4-06 below; confirmed purge is described under M4-07 below. This build preserves and reports unsupported filesystem-operation records.

Batch import (M4-01, `src/library/import-batch.ts`) walks the selection first (stable name order, no directory symlinks, nothing under the root, each device/inode once), then runs each file through `addFileAsNewBook` one at a time. Identical content is detected after staging: live current revisions (archived included) with the same SHA-256 and size are compared byte for byte, and the commit transaction rechecks the hash, so a duplicate is never published or committed. It is rolled back like any failed import (operation `abandoned`). A target section is joined by an `INSERT … SELECT` in the same commit, so a section deleted during the batch leaves the book unfiled with a warning. An `AbortSignal` is checked at every protocol point before the commit; a cancelled copy is rolled back. `library:import` (library window only) opens main's chooser, allows one batch at a time, sends `library:import-progress`, announces `library:changed` after each committed book and returns the summary. `library:cancel-import` aborts it, as do the starting page's destruction or main-frame navigation, including while the chooser is open. The UI receives display names, outcome messages and, for skips, the existing book's ID/title/Archive flag, never managed paths.

Content inspection (M4-02, `src/main/extraction.ts`, `src/renderer/src/extract.ts`) runs sequentially in a disposable sandboxed renderer with its own nonpersistent session and `borges://extract` origin. It has no preload, window assignment or host IPC. That session serves bundled parsing assets and exactly one approved staged file at `/book`; other origins/host paths, permissions, navigation and new windows are denied. PDF.js parses every page's operators, rejects encryption (including empty passwords), reads Info/XMP metadata and renders page one to a thumbnail. The pinned foliate ZIP reader plus detached XML parsing validates EPUB container/package/spine and encryption declarations; only font obfuscation targeting a declared font is allowed. No chapter DOM, script or stylesheet is mounted. EPUB 2/3 raster cover references are decoded to PNG. Covers are a separate optional phase: a decoder failure, crash or resource overrun after validation imports the book with a visible warning and placeholder. Cancellation always rolls the current import back.

The inspector enforces the spec's parser budgets and destroys its window/worker on every exit. A single nonpersistent Electron session is reused to avoid one retained session per book. Production library IPC supplies the inspector as a required dependency; publication/storage tests and controlled catalog seeds deliberately omit the optional low-level `inspect` callback and therefore do not establish content validation. Replacement must reuse inspection before switching revisions.

Extracted title/authors/subjects and the effective values are inserted in the new-book transaction with manual provenance flags clear. Optional metadata is independently validated using the same bounds/subject normalization as manual edits; missing title uses the original filename. An extracted cover has its own existing-schema `cover` recovery operation (`<import-operation-id>-cover`), recorded before file creation. Its staged PNG is synced and durably renamed before the book publication. The final transaction inserts book/revision metadata, effective author/subject rows, cover references and section membership, and marks both operations committed. Before that commit, either operation can be independently rolled back/reconciled; after it, both references and operation states agree. No schema migration is needed. Extracted covers remain distinguishable from later manual corrections through the revision reference and `cover_manual` flag.

Manual replacement (M4-03) reuses the staged copy/inspection/cover-publication path through `replaceBookFile` in `src/library/import.ts`. `src/library/replacement.ts` checks the revision selected before the chooser, then checks it again just before and inside the catalog transaction. Replacement refuses identical content in another live entry, but excludes its own target from that check so an identical original can repair a missing/unreadable managed copy. Explicitly replacing the target with its own identical bytes still creates a revision and resets its new position. An open reader continues reading throughout validation/publication. Immediately before the synchronous switch, `ReaderSessions.quiesce` flushes its latest pending write and durably retires its generation; either failure prevents replacement and retains the session for retry. No event-loop turn separates successful quiescence from the switch. A later precommit failure reloads the unchanged revision with a fresh session.

The replacement transaction inserts the new immutable revision and its extracted metadata/cover, switches the existing book, advances its session generation, refreshes available nonmanual metadata, retires the old revision and inserts its revision Trash entry, and commits both publication operations. It preserves the book ID, status/Archive, memberships and manual metadata (including clears and manual covers); absent extracted values retain useful effective values. The new revision has no position. Old bytes and their revision-specific position remain at their existing relative paths until explicit purge. Zoom remains available for fixed pages; cross-format replacement clears the EPUB font setting, while the reader adapter applies only the sizing its layout supports. No schema migration is needed.

`library:replace-file` is library-only and owns the chooser and bounded inspector; it accepts a book ID, never a renderer-supplied source path. Import and replacement are mutually exclusive. The starting library page's close/reload cancels uncommitted work, including a pending chooser. The one-book selection action explains the position reset and retained old revision before choosing a file. Main reloads the existing reader and updates its title after success; a failed shell reload returns a warning alongside replacement success, instructing the user to close/reopen the reader. Parser/engine failures after shell reload appear in the reader. Neither failure rolls back the committed catalog switch. Trash browsing and deleted-book restore are implemented by M4-05 below; revision restoration is implemented by M4-06 below; purge is implemented by M4-07 below.

Crash before catalog commit leaves old state current plus recoverable staged/published data. Crash after commit leaves the new revision current and old revision recoverable. Startup inspects records, actual paths, and references; filenames alone do not prove cleanup safety. Preserve uncertain data and report repair diagnostics. Record tested durability limits; do not promise power-loss immunity without evidence.

Purge only catalog-confirmed eligible resources. Failed deletion retains a retryable Trash record; an interrupted purge is reconciled without confusing missing Trash bytes with live-file loss. Never implement purge as recursive deletion of the library root or a source path. Restore/delete operations must satisfy the spec even when sections or newer revisions have changed.

## Storage and resources

Agent-selected durable layout:

```text
library/
  catalog.sqlite          catalog, identity/schema, positions, Trash, recovery state
  library.lock            root lock held while Borges runs (see process boundaries)
  library.lock-owner.json holder description while running; diagnostic only
  files/<revision-id>.*   immutable live and recoverable PDF/EPUB revisions
  covers/                 referenced durable covers, including manual corrections
  staging/                operation-scoped incomplete copies
  recovery/               catalog migration snapshots/diagnostics when needed
```

Catalog upgrades (M2-01) run every pending migration in one transaction with foreign keys checked before commit. Before upgrading an existing catalog, a `VACUUM INTO` snapshot is verified (`quick_check`, old version) and renamed into `recovery/catalog-schema-<from>-before-<to>-<time>.sqlite`; snapshots are retained. A catalog is identified by `PRAGMA application_id` and versioned by `user_version`. Newer, foreign, unreadable or damaged catalogs are refused before any write. Damage means the stored schema differs from what the migrations produce from scratch, so manual extra indexes are also refused. Schema 2 (M2-02) adds `books.session_generation` and `positions.generation`. Schema 3 (M3-05) rebuilds `recovery_operations` inside the migration transaction to add the `cover` kind while preserving rows and its partial index.

Trash is catalog state; it need not physically move every file. SQLite sidecars belong with the catalog. Back up the whole root while all application windows are closed, and prove a copied root works without the original path. Default root follows the [XDG base-directory convention](https://specifications.freedesktop.org/basedir/latest/). External runtime caches/logs are disposable.

Render current pages and bounded adjacent resources for open books only. Dispose workers/documents/object URLs/image buffers/listeners on close. Manual cover correction validates in main (PNG/JPEG, at most 10 MiB, 16 megapixels, 8192 pixels per side) and stores a raster thumbnail at most 512×768. `library:choose-cover` opens the local file dialog; `library:cover` returns only the current book’s approved bytes after a token and canonical `covers/` path check. Both channels enforce library-window sender identity; neither exposes a general file path API. The grid requests covers near the viewport with at most four reads/decodes in flight and releases blob URLs when cards leave the viewport or unmount. Missing/unusable covers keep the initials/format placeholder; the compact list loads no covers. Browsing 500 entries must not instantiate 500 readers. Make long searches cancellable and incremental. Diagnostic packaged budgets are recorded in [M1-07 evidence](development.md#packaged-runtimeresource-measurements-m1-07); catalog/500-entry budgets are recorded by A13 and extended to cover-bearing browsing in [M3-08 evidence](development.md#cover-bearing-catalog-measurements-m3-08). M1-07 observed that the earlier shared `borges://reader` site placed all book content in one renderer. M5-04 reproduced the resulting two-book failure and introduced per-book sites, with native process-death/recovery checks. Packaged A13 remeasurement must retain distinct simultaneous content processes and observe disposal of both after readers close; see [M5-04 evidence](development.md#reader-crash-containment-m5-04).

## Import metadata choices (M4-04)

After staged-byte validation and extraction, `metadataDuplicates` (`src/library/duplicates.ts`) compares the nonempty extracted title and authors against effective metadata on every live current revision, including archived entries. It uses `foldKey`, requires an equal title and at least one shared nonempty author, and never substitutes a filename for missing extracted title metadata. Byte-identical detection still precedes extraction and skips without a metadata prompt.

The batch pauses on a library-only `library:import-duplicate` event carrying display metadata, all candidates and a fresh token. `library:resolve-duplicate` validates sender, token and choice; the publication service restricts replacement to a candidate from that prompt and retains its previewed revision ID for the existing precommit/transaction checks. A token is consumed once. Cancel, page navigation or destruction aborts the pending choice and rolls back the staged operation.

Keep Both continues new-book publication and joins the selected section. Skip rolls back without adding memberships. Replace changes the staged operation's kind and owning book to the selected target before cover publication, then uses the same revision switch, strict reader quiescence, Trash retention and reconciliation as manual replacement. No second source read or inspection is needed after a choice. The batch reloads a retired reader on success or precommit failure; a committed replacement whose reader reload fails remains successful with a warning. Replacement summaries explain old revision retention and do not claim to join the import section. The schema is unchanged.

## Delete and deleted-book restore (M4-05)

`src/library/trash.ts` implements soft deletion, deleted-book restore and Trash listing. Bytes stay at their immutable relative paths: these two actions mutate only catalog state, so one SQLite transaction covers the entire persistent transition and needs no separate filesystem recovery operation. Delete inserts a book Trash entry with a snapshot of section IDs/names, sets `deleted_at` and advances the session generation together. Positions, sizing, manual metadata/provenance, status/Archive, memberships and prior revision Trash entries remain intact. Restore clears deletion, advances the generation, restores surviving memberships and removes only the book Trash entry together. Deleted sections are never recreated; their snapshot names are returned for explanation. Existing schema 3 suffices.

Main's library-only `library:delete-book` calls `WindowCoordinator.closeCatalogReader` before deletion. The coordinator temporarily denies all authority to that reader page and prevents reopening its book, calls strict `ReaderSessions.quiesce`, requests close and requires the observed `closed` event (a two-second refusal timeout preserves the live entry). A save/retirement failure prevents close/deletion. A failed close reloads the still-live reader with a fresh session; a failed catalog commit leaves the book live with its saved position, even if its reader already closed. Import, replacement and Trash writes are mutually exclusive, and other catalog mutations are rejected during a pending Trash action. UI selection deletion reports each book independently, including partial failure. Action errors survive successful catalog refreshes.

`library:restore-deleted-book` rejects stale/non-book Trash entries and refuses a hash/size match in another live current entry, archived included; main opens/activates the existing entry and explains the conflict. Restore of a missing/unreadable managed file explicitly warns that only the catalog entry was restored and directs the user to Replace File. No sources or managed bytes are changed. Revision restore and Trash-only import choices are implemented by M4-06 below; purge is implemented by M4-07 below.

`library:trash` lists deleted books and superseded revisions with their filenames, formats, retained positions and deletion dates. It opens only canonical root-confined record-named files, rejects nonregular files, and sums each referenced file/cover path once. Missing/unreadable references remain visible and are excluded from the total. This is logical retained file size, not allocated filesystem blocks or a reclaimable-space estimate; shared covers may also have live references. Known superseded cover publications of deleted books are included as described under M4-07; other unreferenced covers and recovery artifacts are outside this total. No book reader or cover decoder is instantiated for Trash browsing.

## Revision restore and Trash-only import matches (M4-06)

`src/library/revision-restore.ts` verifies a retained regular file's recorded size and SHA-256 before either restore mode. Restoring as current is a catalog-only transaction: recheck the Trash entry and previewed current revision, reject any identical live current content (including Archive), flush/retire an open reader synchronously, use the replacement metadata/retirement logic, unretire the selected revision and remove its revision Trash entry. Its existing position is retained; the displaced revision and location become Trash. Main reloads the reader on success or precommit failure. Postcommit reload failure is a warning alongside committed success. A deleted owner must first be restored as a book; its old files may still be copied separately.

Separate restoration uses the established import publication protocol to copy retained bytes to a new immutable revision. It creates an Unread, unarchived, unfiled entry at the beginning with extracted metadata/cover, without manual overrides or memberships from the owner. The original revision/location stay in Trash, explicitly explained in both dialogs. Stored cover reads are bounded and regular-file-only. The copy must match the verified digest, and the source Trash/current-revision snapshot is rechecked inside the final transaction. Its `import`/`cover` operation records already provide rollback/reconciliation; no new schema or operation kind is needed.

`trashCandidates` (`src/library/trash-matches.ts`) finds matching deleted current revisions and superseded revisions by hash/size. Normal new-book imports check live equality first, then Trash before extraction. A Trash match pauses on the library-only `library:import-trash-match` event. The token-bound `library:resolve-trash-match` response must select an advertised entry and an available restore mode, or cancel this file. Deleted-book restore retains its old state/memberships; current-revision restore uses the same reader coordination; separate reuse makes an independent copy. Restoration leaves the import section untouched. Completed restores have their own per-file `restored` outcome; the redundant staged source copy is rolled back through the original import operation. Source files are never mutated. A failed cleanup stays tracked for startup recovery.

Tokens are single-use. Library destruction/navigation or Cancel import aborts a waiting choice and all precommit restoration work, including the async deleted-book file check. The candidate snapshot, duplicate-live check and final transaction are revalidated; normal import also refuses a newly appeared Trash hash rather than silently adding it. Explicit manual replacement remains an explicit replacement, and separate restoration uses a private bypass to avoid prompting about the very retained bytes being reused. Neither bypass is renderer-controlled. No-match imports still use ordinary metadata-duplicate choices.

## Empty Trash and interrupted purge (M4-07)

`src/library/purge.ts` plans one deleted book with all its revisions, or one superseded revision of a live book. The library-only `library:empty-trash` endpoint requires the displayed entry IDs and retained-byte total, refuses stale confirmation and serializes removal against other catalog writes, import/replacement and an outstanding cover chooser. The dialog explains permanent loss, shared-cover retention and unchanged sources. Confirmed work continues if the library page closes/reloads; startup resumes unfinished work before opening windows.

Before any unlink, a `purge` recovery operation commits in `pending` state with entry/revision IDs, root-relative paths and recorded publication digests. Each retry re-derives the plan from current catalog ownership and Trash state. Only canonical record-owned regular files with matching size/SHA-256 are removed, followed by directory fsync. Missing files in a confirmed operation are accepted and the directory is synced again. Symlinked managed directories, final symlinks, modified bytes and uncertain ownership are retained. No source path or recursive removal is used. Effective/extracted covers and accounted-for superseded cover publications of a deleted book are candidates; any reference from another book/revision or unfinished publication preserves that cover. Unknown files remain outside purge and continue to produce startup diagnostics.

The book/revision, position, metadata, settings, memberships and Trash rows are removed in one final transaction with the operation's `committed` state. A failure before that leaves the Trash/catalog rows and durable pending intent for retry; some bytes may already be gone. Such entries show the saved error across refresh/restart, and all restoration modes (including import choices) and deletion of that owning book are refused until the confirmed purge finishes. This prevents partially deleted bytes from being made live. A failure to create the initial intent removes no bytes and saves its explanation in the Trash entry's existing context. Removed cover publications retain their history with `detail.purgedBy`, committed with final cleanup; later listings exclude those intentionally removed files. Retry plans still include publication history so another completed purge cannot invalidate an existing plan. No schema migration is needed.

Trash storage totals now also include accounted-for superseded covers belonging to deleted books, once per path. Shared covers can remain after purge, so the displayed file lengths are still not a promise of freed blocks. Process-kill tests cover durable intent, first unlink, all file/cover removals, final catalog transaction and postcommit state; they do not establish power-loss behavior.
